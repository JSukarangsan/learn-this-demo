# Projects

Read on top of `../CLAUDE.md`. One folder per piece of work in flight.

Everything above this folder is true regardless of what we're building this quarter — the
glossary, the constraints, the tokens, who owns what. Everything in here is true of exactly
one project and stops being true when that project ships.

**If you find yourself writing something here that would still be true after this project
ends, it belongs upstairs.** That is the whole rule, and it's the one that keeps a project
folder from slowly becoming a second copy of the team's context.

## The shape

```
<project>/
├── CLAUDE.md                what this is, and what already bit us
├── comms/                   what was said, and what we told people. Never canonical.
└── deliverables/
    ├── requirements/        what we're building and how we'll know it's done
    ├── research/            evidence. What we learned, and from whom.
    ├── design/              states and flows for this project only
    └── launch/              how it goes out, and what we watch after
```

`deliverables/` is split by **the stage of work that produced the artifact**, not by what
the artifact is. A brief and an acceptance list are different documents that come out of
the same conversation, so they sit together. The reason to organise it this way is that
when something new gets made, the stage it came from is usually obvious and its file type
usually isn't — so the folder tells you where to put it without anyone having to decide.

## Folders appear when there is something to put in them

**Do not scaffold the empty ones.** An empty `launch/` on a project nobody has started
tells a reader — and an agent — that a launch plan exists somewhere and they failed to
find it. Nothing is a better signal than an empty folder pretending.

This means the four projects in here don't look alike, and that's the point. You can read
the state of the work off the tree:

| | State | What exists |
|---|---|---|
| `cohort-scheduling/` | in build | all four stages |
| `enrollment/` | shipped, still learning | requirements, and the meeting that found a gap |
| `search-relevance/` | scoped | requirements |
| `video-playback-v2/` | not started | `CLAUDE.md` and an honest list of what nobody has decided |

Read that column as **`deliverables/`**. `comms/` is the exception to the rule above and
appears on all four, including the project nobody has started — because we report on a
project before we build it, and a status file saying *blocked, still not scheduled* is
exactly the kind of thing that has nowhere else to go.

## `comms/` — the unprocessed layer, and there is no copy of it upstairs

Everything we said about a project, and everything anyone said in a room about it, lives
in that project's `comms/`. There is no squad-level `comms/`. A status report that covers
three projects gets split across their three folders rather than filed somewhere none of
them would look.

Two kinds of file live here, they are not canonical for **opposite** reasons, and telling
them apart is the whole job:

| | | |
|---|---|---|
| `<date>-<what-it-was>.md` | **Input.** What was said. Written by a person, never edited after. | Not canonical because nobody filtered it yet |
| `<date>-status.md` | **Output.** What we told people. Generated by `/weekly-digest`. | Not canonical because somebody already filtered it |

A raw transcript and a status report read alike to a model — both are prose, both are
dated, both describe the project. But one is evidence and the other has already been
through somebody's judgment about what mattered that week. Cite them the same way and you
end up quoting a summary of a summary.

**On the raw notes.** Raw is the point — do not clean them up; a tidied transcript has
already thrown away the half-sentence that turns out to matter three weeks later. And
nothing in one is a decision. Someone proposing something reads exactly like someone
deciding it, and the proximity here is what makes it dangerous: **a note sitting next to
that project's requirements is still not a requirement.** If a meeting settled something,
the decision goes in `../../product/decisions/` and the note stays as the transcript that
led to it. When you cite one, say it came from a meeting and name the date.

**On the status files.** Derived, not authored — every line came from somewhere else in
the repo. If a status file and its source disagree, the source is right and the file is
stale. **Regenerate rather than patch:** fixing a wrong line here fixes one document,
fixing the file it came from fixes every future report too. They're kept as a record of
what the team was told and when, which is genuinely useful when somebody says *nobody
mentioned this*. They are not kept because they're true.

**Dating.** Date-prefix everything: `2026-08-04-<what-it-was>.md`. The date is the
meeting, or the week covered — never the day someone got around to filing it.

## What a project `CLAUDE.md` is for

Not a summary of the folder — an agent can read the folder. It's for the things that are
true about this project and written down nowhere else: the mistake we already made, the
thing that is settled and keeps getting re-proposed, the constraint that isn't obvious
until you've hit it.

Each one is three or four paragraphs. If yours is getting long, most of it is either a
requirement (`deliverables/requirements/`) or team context (upstairs).
